# Fuentes gratuitas y modelos locales de LitMate

Revisión e implementación del 20 de octubre de 2026. Este documento complementa `INFORME_BUSQUEDA_LITERARIA.md`. Las pruebas de fuentes descritas aquí usan HTTP real, sin cargar `.env`, sin consultar TiDB y sin ejecutar migraciones. No se ha modificado la interfaz, las tarjetas, la voz ni los avatares.

## Continuación del 21 de octubre: ediciones y procedencia

Se completó la recuperación oficial de ediciones en `core/literary_search.py`. Search API puede devolver ediciones anidadas en cada obra; si el registro de obra carece de descripción, se permite consultar su endpoint oficial `editions.json?limit=5`. Entre ambos tipos de detalle se ejecutan como máximo **dos GET adicionales por búsqueda temática**, compartiendo el límite de páginas y los 15 segundos de investigación externa existentes. Una descripción ya disponible evita pedir otro registro. Un acierto de caché no consume una nueva solicitud HTTP ni un espacio de lectura.

La edición debe aportar un identificador `/books/OL…M`, un título compatible y un vínculo a la obra correcta. Una relación `works` explícita nula, inválida, múltiple o dirigida a otra obra se rechaza, aunque la edición aparezca anidada. El vínculo documentado de Search API solo sustituye la relación `works` cuando esta no está presente. Se conservan las validaciones de títulos de saga y de idioma solicitado, y se admiten únicamente ISBN con suma de control válida. No se cambia el título o autor del registro de obra por datos de una edición, ni se siguen URLs aportadas por esos registros. Documentación: [ediciones en Search API](https://openlibrary.org/dev/docs/api/search), [Works y Editions API](https://openlibrary.org/dev/docs/api/books).

Se corrigieron dos errores concretos de procedencia: un subtítulo sin descripción ya no recibe una URL de sinopsis, y una descripción no puede reemplazarse conservando la URL del texto anterior. Los subtítulos enriquecen los metadatos y pueden orientar la recomendación, pero **no se convierten en sinopsis**. Las descripciones de obra y de edición conservan su origen real. Los textos genéricos como «Publisher description» se descartan. Los códigos 429, 403 y 401 en lecturas de detalle activan el cooldown de Open Library para evitar consultas repetidas; las fichas válidas ya obtenidas se conservan sin rellenar información faltante.

La comprobación real `reportes/ediciones_openlibrary_20261021.json` consultó «estoy buscando un libro sobre arte japonés» sin cargar `.env`, sin modelo conversacional y con SQLite en memoria. Obtuvo cinco obras en **3,164 segundos**, mediante un GET de búsqueda, uno de obra y uno de ediciones: dos espacios de lectura y ninguna búsqueda web lógica. Se recuperó el subtítulo bibliográfico de [Legend in Japanese art](https://openlibrary.org/works/OL182055W), además de otros subtítulos incluidos en la respuesta de Search API. Ninguno de los registros consultados ofreció una descripción utilizable: se registraron cero caracteres de sinopsis y no se inventó una. La consulta equivalente inmediata reutilizó la caché, con **cero solicitudes HTTP nuevas**. El informe conserva identificadores, URLs y cantidades, sin almacenar los cuerpos completos de los registros.

Las **21 pruebas controladas nuevas** de `core/test_openlibrary_editions.py` comprueban estos límites, el rechazo de cruces entre obras, idioma, ISBN, errores de API y caché. La ejecución focalizada junto a `core.test_progressive_free_sources` y `core.test_free_topic_recommendations` terminó con **78 pruebas aprobadas**. Esta prueba de integración real demuestra recuperación bibliográfica y reutilización de caché; no mide por sí sola la calidad de una respuesta del modelo ni demuestra una tasa de error del 1 %.

Open Library documenta un límite general de un GET por segundo para peticiones no identificadas; LitMate conserva ese límite conservador. Para uso regular debe configurarse un contacto público de la aplicación mediante `LITMATE_BOOKS_CONTACT`, sin tomar correos ni datos del lector. La política actual prioriza consultas interactivas, caché e identificación de la aplicación, y prohíbe usar la API como backend masivo o infraestructura comercial de mucho tráfico. Un despliegue con esa escala necesitaría revisar las condiciones y valorar los dumps públicos; la prueba local no concede capacidad ilimitada. [Política oficial de uso](https://openlibrary.org/developers/api).

## Qué se ha corregido en la recuperación

`core/literary_search.py` conserva el catálogo Django, las fichas locales y los fragmentos del RAG como primera etapa. Open Library y la integración opcional de Google Books aportan registros bibliográficos. La investigación adicional conserva SearXNG local, Wikipedia, Wikidata y el extractor público existente; no sustituye al asistente por otro servicio.

Una lista de materias no se convierte en una sinopsis. El enriquecimiento ahora exige un pasaje obtenido de una página o una API oficial y una identidad compatible con la obra: título exacto o alias ya confirmado y autoría completa. Una coincidencia secundaria del título, un apellido compartido, un volumen distinto de la saga, un fragmento del buscador o una página marcada con instrucciones maliciosas no completan la sinopsis. La evidencia aceptada conserva el vínculo interno con la obra y su URL; el resumen recuperado permanece separado de la sinopsis bibliográfica original.

Se ha ampliado Wikipedia de manera progresiva: español primero; inglés si no hay resultados o si los títulos devueltos son tangenciales a la consulta. La aparición de un artículo en el buscador no lo convierte automáticamente en información sobre el libro. El sistema sigue verificando esa correspondencia. La documentación oficial permite buscar mediante la API y recomienda limitar, identificar y ordenar las solicitudes; las dos búsquedas de sinopsis complementarias se ejecutan en serie. Fuentes: [API de búsqueda de MediaWiki](https://www.mediawiki.org/wiki/API:Search), [política de uso de la API](https://www.mediawiki.org/wiki/API:Etiquette).

Para las búsquedas del mismo autor, se traduce `inauthor:` de Google a `author:` de Open Library; `intitle:` se traduce a `title:`. Una solicitud explícita en español añade `language:spa`, y se descartan resultados sin ese idioma documentado. Los idiomas de una obra en Open Library agrupan ediciones: esto no demuestra que su portada o fecha genérica pertenezcan a una edición española específica. Fuentes: [Search API de Open Library](https://openlibrary.org/dev/docs/api/search), [política de APIs](https://openlibrary.org/developers/api).

`core/literary_sources.py` incorpora trazas sin preguntas, URLs, pasajes ni datos personales: proveedor, operación, estado y cantidad. `research_snapshot()` distingue búsquedas lógicas, solicitudes HTTP iniciadas, espacios de lectura reservados y páginas efectivamente extraídas. Una búsqueda complementaria intentada no equivale a haber obtenido una sinopsis. Los resultados de caché tampoco cuentan como nuevas solicitudes HTTP.

La memoria de peticiones de `core/literary_conversation.py` conserva ahora hasta cuatro temas recientes durante una hora, separados de las respuestas aceptadas y sus fuentes. La secuencia Corea → arte japonés → «volvamos a la historia de Corea» restaura el tema anterior incluso si alguna respuesta falló. Solo un retorno explícito con pistas suficientes selecciona un tema: «volvamos al tema anterior» o «volvamos a Corea» cuando existen dos temas coreanos distintos no generan una consulta por adivinación. El historial mínimo contiene únicamente tema saneado, intención y fecha; no guarda respuestas fallidas, libros, fuentes ni pasajes. Las referencias a personajes y obras concretas siguen perteneciendo al resolvedor bibliográfico. Trece regresiones nuevas cubren el retorno, cambios de tema, ambigüedad, privacidad, expiración y el endpoint Django; la ejecución focalizada de memoria e identidad terminó con 56 pruebas aprobadas.

## Fuentes y límites de integración

| Fuente | Uso en LitMate | Límites y decisión |
| --- | --- | --- |
| Open Library | API oficial de búsqueda y registros de obras; autor, título, materias, portadas y descripciones cuando existen | Sin clave obligatoria. Control de un GET por segundo en el caché configurado, caché de resultados y registros, tiempo compartido y máximo de dos registros de detalle por consulta temática. No ofrece todas las sinopsis ni el contenido completo. |
| Google Books | Integración existente conservada y opcional | No se activa una clave antigua por sí sola. Se mantienen la política de costo cero y la confirmación de configuración sin facturación. La documentación exige identificación de la aplicación para los datos públicos; no se ha sustituido por peticiones anónimas ni scraping. [Documentación oficial](https://developers.google.com/books/docs/v1/using). |
| SearXNG | Instancia Docker del mismo equipo, API JSON | Contenedor saludable en `127.0.0.1:8080`. Motores configurados: Wikipedia, Open Library y Mwmbl. Sin claves comerciales ni dependencia de instancias públicas. Sus resultados dependen de la cobertura y disponibilidad de esos motores. [API oficial](https://docs.searxng.org/dev/search_api.html). |
| Wikipedia | APIs oficiales en español y, cuando hace falta, inglés | Información secundaria. Los artículos y su correspondencia con la obra requieren verificación. No garantiza personajes, capítulos ni citas exactas para todos los libros. |
| Wikidata | Integración existente de entidades y relaciones verificables | No representa un catálogo completo de personajes o acontecimientos. La ausencia de una relación no demuestra que el personaje no exista. |
| Editoriales y bibliotecas autorizadas | Localización por SearXNG y extracción acotada, con robots, DNS público y TLS | Solo se recuperan pasajes breves; no se incorporan automáticamente libros completos al índice permanente. Se mantiene la lista de lectura autorizada y la protección contra redes privadas y redirecciones. |
| Amazon, Buscalibre, Casa del Libro, Goodreads, Barnes & Noble, Gandhi | Nuevo descubrimiento de enlaces y fragmentos que entregue SearXNG | Una lista separada permite conservar esos enlaces sin autorizar la extracción de sus páginas. No se consulta una API privada, no se afirma disponibilidad/precio y no se eluden restricciones. No se ha probado que los motores encuentren una página comercial para cada consulta. |
| WorldCat | Descubrimiento de enlaces públicos mediante SearXNG | Sin integración directa de API. La documentación de OCLC exige elegibilidad institucional y suscripciones para Search API; no se añade como requisito gratuito. [OCLC](https://www.oclc.org/developer/api/oclc-apis/worldcat-search-api.en.html). |
| Library of Congress | Evaluación del endpoint JSON oficial y descubrimiento de enlaces | La API pública documenta acceso sin clave y 20 solicitudes por minuto, pero las tres consultas reales realizadas desde este equipo recibieron HTTP 403. No se evade el bloqueo ni se agrega un adaptador obligatorio que aquí falla. [Límites oficiales](https://www.loc.gov/apis/json-and-yaml/working-within-limits/). |
| Biblioteca Nacional de Chile, Biblioteca Nacional Digital y Memoria Chilena | Se conserva la consulta legítima de páginas autorizadas; se amplía el descubrimiento de enlaces institucionales | No se inventa una API pública estable. La información sobre restricciones de acceso a objetos digitales se respeta. La documentación institucional localizada no permite asegurar una API de consulta general accesible para esta aplicación. [Acceso al buscador institucional](https://www.bibliotecanacional.gob.cl/servicios/acceder-nuestro-buscador). |
| Goodreads API | Sin integración directa | Goodreads informa que no emite nuevas claves de desarrollador y prevé retirar las herramientas actuales. Se conservan solamente los enlaces descubiertos; no se utiliza un endpoint interno no documentado. [Aviso en su grupo oficial](https://www.goodreads.com/group/show/8095-goodreads-developers). |

La lista de dominios para descubrir enlaces no amplía la lista de sitios que el extractor puede visitar. Las direcciones privadas, credenciales en URLs, puertos no autorizados y dominios que imitan a los oficiales siguen bloqueados. No se realiza scraping de resultados HTML de Google ni se copian respuestas generadas por buscadores.

## Hardware y modelos

Se observaron 31,9 GiB de RAM física, un AMD Ryzen 5 5500X3D de 6 núcleos y 12 hilos, y una NVIDIA GeForce RTX 4060 con 8.188 MiB de VRAM. En la muestra inicial había 4.627 MiB de VRAM libres y aproximadamente 16,9 GiB de RAM disponibles; estos valores cambian según los programas abiertos. Se comprobaron aproximadamente 337 GiB libres en C: y 106 GiB en G: antes de descargar el candidato.

Modelos disponibles inicialmente: `qwen3.5:9b-q4_K_M`, 6,6 GB, y `embeddinggemma:latest`, 621 MB. No se retiran ni se sustituye automáticamente su configuración. El tamaño de los pesos no equivale al consumo total: contexto, cachés de atención y otros programas también ocupan RAM/VRAM.

El primer candidato descargado fue **`qwen3.5:4b`**, desde la biblioteca oficial de Ollama: manifest local `d8b0f5e9760c`, 3,3 GB, cuantización Q4_K_M y licencia Apache 2.0. El menor tamaño fue un motivo para medir su rendimiento en esta GPU, no una prueba de mayor precisión. El ensayo real de tres consultas (`reportes/validacion_temas_20_oct_4b.json`) tuvo dos respuestas rechazadas y una respuesta inicialmente aceptada que solo saludaba: ese saludo no constituye una recomendación correcta y motivó una regresión adicional de validación. No se modificó `.env` ni el modelo predeterminado durante la instalación. Fuentes: [Ollama Qwen 3.5 4B](https://ollama.com/library/qwen3.5:4b), [ficha oficial de Qwen y licencia](https://huggingface.co/Qwen/Qwen3.5-4B).

También se probó Qwen 3.5 9B con contexto de 8.192 tokens. La primera clasificación terminó con `ollama_sin_respuesta_valida` tras 240 segundos; el resultado está en `reportes/validacion_final_9b_contexto8192.json`. Durante esa carga se observaron 7.621 de 8.188 MiB de VRAM ocupados, GPU al 100 % y el cargador del codificador visual activo, aunque el mensaje era textual. Estos datos muestran presión de recursos; no prueban por sí solos una causa única del bloqueo. Se detuvo la repetición del ensayo fallido y se descargó ese modelo de memoria mediante la API local, sin apagar Ollama. No se presenta ese intento como inferencia exitosa ni como mejora.

Como segundo candidato se instaló y verificó **`qwen3:8b`**, un modelo de texto sin codificador visual: 5,2 GB, ID local `500a1f067a9f`, cuantización Q4_K_M y licencia Apache 2.0. Su ficha oficial lo identifica como modelo causal de generación de texto y la API local confirma capacidades de texto, herramientas y razonamiento, sin visión. La comparación tiene una hipótesis concreta: evitar el coste de cargar visión en un chat textual y mantener más capacidad que 4B. El resultado debe medirse con las mismas preguntas antes de seleccionarlo. No se agregan otros modelos: el conjunto conversacional queda limitado al 9B original y estos dos candidatos. `reportes/modelos_hardware_20261020.json` conserva hardware y capacidades obtenidas mediante lectura de metadatos, sin ejecutar inferencias ni cambiar el modelo predeterminado. Fuentes: [Ollama Qwen3 8B](https://ollama.com/library/qwen3:8b), [ficha oficial Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B).

Los modelos de 12B o 27B no se instalan como respuesta automática a los errores: sus pesos y contexto pueden exceder la VRAM del equipo, y no hay una comparación local que justifique esa descarga. Tampoco se agrega un modelo de reranking sin una evaluación que demuestre su beneficio. La decisión entre Qwen 3.5 9B, Qwen 3.5 4B y Qwen3 8B debe tomarse con las mismas consultas, validadores y evidencias, diferenciando carga inicial, latencia y calidad; los resultados del ensayo completo del asistente se registran en el informe general de esta continuación.

## Costo obligatorio de API y pendientes reales

Ningún cambio de este informe requiere clave comercial, tarjeta, suscripción o cobro por solicitud. Ollama, los modelos descargados y SearXNG funcionan en el equipo. El costo de API obligatorio sigue siendo **$0**; esto no significa consumo nulo de electricidad, disco o conexión. Los proveedores bibliográficos no ofrecen disponibilidad ilimitada ni garantía de permanencia.

Permanecen límites concretos: la cobertura de Mwmbl y de los catálogos es incompleta; algunas obras solo tienen materias; las fuentes pueden discrepar o bloquear solicitudes; las portadas y los idiomas deben verificarse por edición cuando se pide una edición exacta. El sistema debe expresar incertidumbre cuando no consiga respaldo, y seguir investigando solo dentro de los presupuestos compartidos existentes.

La aplicación completa conserva dependencias ajenas a esta búsqueda, como la base principal configurada en el entorno y la caché Redis opcional. Este trabajo no cambia la cuenta, el plan ni la facturación de TiDB u otros servicios que el usuario tenga contratados. El proveedor de generación y los embeddings del asistente permanecen locales; Pinecone está deshabilitado en la configuración de IA.

Para comprobar solo las nuevas regresiones, sin la base de producción:

```powershell
.\venv\Scripts\python.exe -B verificar_proyecto.py core.test_progressive_free_sources core.test_free_topic_recommendations
```

Para la comparación del chat deben emplearse los verificadores aislados del proyecto, no `manage.py test` con la configuración normal que carga la base principal. La instalación del candidato es reversible y no requiere migraciones.
